2. 기본 수정·저장 절차

  1. https://cnu-fpft-lab.github.io/manage/에 접속해 GitHub로 로그인합니다.
  2. 왼쪽 메뉴에서 수정할 데이터 종류를 선택합니다.
  3. 필드를 수정하고 이미지가 필요하면 기본 미디어 선택기를 사용합니다.
  4. 저장 전 ID, 제목, 날짜, 이미지가 의도대로 들어갔는지 확인합니다.
  5. 편집 화면 상단의 Decap 저장/발행 버튼으로 확정합니다.
  6. GitHub Pages 배포 후 홈페이지에서 최종 확인합니다.
저장 버튼이 비활성화되어 있으면 실제 데이터 값이 바뀌지 않은 상태일 수 있습니다. 특히 이미지는 미디어 창에서 ‘선택한 것으로 결정’까지 해야 필드 변경으로 인식됩니다.

3. 구성원 관리

PI

이름, 영문명, 직위, 이메일, 전화, 교수실, 소개, 프로필 사진을 관리합니다. 프로필은 세로 사진을 권장하며 홈페이지에서 정해진 프레임에 자동 맞춤됩니다.

학생

이름, 영문명, 과정, 이메일, 프로필 사진을 관리합니다. 과정 값은 CMS에 지정된 선택값을 사용하는 것이 안전합니다.

기존 학생을 수정할 때는 다른 학생 행을 삭제하지 않도록 주의합니다. 큰 구조 수정 전에 현재 내용을 한 번 확인한 뒤 저장하세요.

4. Research 관리

ID페이지 식별에 사용됩니다. processing, foodtech 같은 기존 ID는 특별한 이유가 없으면 변경하지 않습니다.
번호현재 Research 01 / 02 구조와 맞게 유지합니다.
대표 인포그래픽가로 약 1500 px 이상 원본 권장. PNG/JPG/WebP 등을 올리면 홈페이지가 화면 크기에 맞춰 자동 축소합니다.
연구 흐름단계 순서를 바꾸면 Research 페이지의 흐름 표현도 바뀔 수 있으므로 저장 전 순서를 다시 확인합니다.
세부 연구주제 Figure원본 비율을 유지하도록 설계되어 있으므로 불필요하게 저해상도로 줄이지 않습니다.
메인화면 이미지 별도 관리: Research 페이지의 대표 인포그래픽과 홈페이지 상단 hero는 별도 요소입니다. 현재 hero 구성은 HTML/JS와 기존 이미지 데이터에 의존하므로 Research 이미지 필드만 교체해서는 홈 배경이 반드시 함께 바뀌지 않습니다.

5. 이미지 교체 절차

  1. 이미지 필드를 눌러 Decap의 이미지 창을 엽니다.
  2. 새 원본 파일을 업로드합니다.
  3. 목록에 나타난 새 이미지 썸네일을 클릭합니다.
  4. 초록색 ‘선택한 것으로 결정’을 누릅니다.
  5. 편집 화면으로 돌아왔을 때 이미지 필드가 새 파일로 바뀌었는지 확인합니다.
  6. Decap의 저장/발행 버튼을 눌러 GitHub에 반영합니다.
미디어 창의 ‘다운로드’, ‘이름 복사’, ‘선택항목 삭제’는 일반적인 이미지 교체 과정에서는 사용하지 않습니다. 기존 파일 삭제는 해당 파일을 쓰는 다른 페이지까지 영향을 줄 수 있습니다.

6. 학생 관리자 등록 절차

준비: 학생에게서 이메일이 아닌 정확한 GitHub username 또는 https://github.com/사용자명 프로필 주소를 받습니다. 이메일만으로 Worker 허용목록의 ID를 확정하지 않습니다.

6-1. GitHub 저장소 Write 권한 부여

  1. 권한이 있는 GitHub 계정으로 CNU-FPFT-Lab/cnu-fpft-lab.github.io를 엽니다.
  2. Settings → Collaborators and teams(UI 표시가 다를 수 있음)에서 Add people / Add collaborator를 선택합니다.
  3. 학생의 확인된 username을 검색해 초대합니다. 이 저장소에는 Write 권한만 부여하고 Maintain / Admin / Organization Owner는 부여하지 않습니다.
  4. 학생이 자신의 GitHub 계정에서 초대를 수락했는지 확인합니다.

6-2. Cloudflare OAuth 학생 허용목록 갱신

  1. 저장소의 oauth-proxy/wrangler.toml을 열어 기존 MANAGER_GITHUB_USERS = "dkrnd2"는 유지합니다.
  2. STUDENT_GITHUB_USERS = ""를 정확한 username으로 바꿉니다. 여러 명이면 쉼표로 구분합니다.
  3. 교수 계정은 MANAGER_GITHUB_USERS에만 유지합니다. 학생을 이 항목에 넣지 않습니다.
  4. Cloudflare Worker 배포 권한이 있는 PC에서 저장소 최신본을 받아 oauth-proxy 폴더로 이동하고 아래 명령으로 재배포합니다.
STUDENT_GITHUB_USERS = "CONFIRMED_STUDENT_USERNAME"

다음은 실제 배포 명령입니다.

git pull
cd oauth-proxy
npm install
npx wrangler login
npm run deploy

이미 oauth-proxy 디렉터리 안에 있다면 cd를 반복하지 않습니다. GITHUB_OAUTH_ID, GITHUB_OAUTH_SECRET, STATE_SECRET는 비밀값으로 유지하며 공개 저장소나 매뉴얼에 기록하지 않습니다.

GitHub Pages 배포와 Cloudflare Worker 배포는 서로 다릅니다. wrangler.toml을 GitHub에 저장한 것만으로는 현재 실행 중인 Worker의 허용목록이 바뀌지 않습니다. 이 매뉴얼은 저장소 설정을 기준으로 작성되었으며 Cloudflare의 실제 배포 버전은 별도로 확인해야 합니다.

6-3. 최종 권한 확인

  1. 교수 계정(dkrnd2)으로 /manage/와 /admin/에 각각 로그인하여 편집 메뉴를 확인합니다.
  2. 학생 본인 계정으로 /admin/ 로그인 및 공지 등 일반 필드의 저장 기능을 확인합니다.
  3. 학생 계정으로 /manage/를 시도했을 때 인증이 거부되는지 확인합니다. 공개 페이지 자체가 보일 수 있어도 교수용 토큰 발급은 거부되어야 합니다.
  4. 테스트용 문구를 공개 사이트에 장시간 남기지 말고 즉시 원복합니다.

6-4. 권한 제한의 실제 수준

CMS 화면학생은 /admin/의 공지·논문·활동·과제만 편집하도록 메뉴가 구성되어 있습니다. 교수는 /manage/의 여섯 분류를 편집합니다.
GitHub Write중요: 학생에게 필요한 Write 권한은 GitHub에서 저장소 파일을 직접 수정할 수 있는 강한 권한입니다. /manage/ 경로의 OAuth 제한은 GitHub에서 직접 HTML·JS·Research JSON을 수정하는 행위까지 차단하지 않습니다.
현재 승인 방식두 CMS 모두 main에 직접 기록하는 설정입니다. 학생 수정의 교수 승인 후 병합(PR) 워크플로는 현재 구성되어 있지 않습니다.
더 엄격한 통제별도 제출 브랜치+PR 승인, GitHub 브랜치 보호/규칙셋, 파일별 보호가 필요한 경우 서버측 인증을 추가하는 재설계가 필요합니다. 이는 현재 구현된 기능이 아닙니다.

6-5. 담당 종료·권한 회수

  1. GitHub의 해당 저장소에서 학생의 Write 접근 권한을 제거합니다.
  2. STUDENT_GITHUB_USERS에서 해당 username을 삭제하고 Cloudflare Worker를 재배포합니다.
  3. 학생이 보유할 수 있는 불필요한 개인용 접근 토큰과 OAuth 승인 앱도 점검하고 필요한 경우 회수하도록 안내합니다.

7. 잘못 저장했을 때 복구

  1. 문제를 발견하면 같은 화면에서 여러 차례 추가 저장하지 않습니다.
  2. GitHub 저장소의 최근 commit history에서 어떤 파일이 바뀌었는지 확인합니다.
  3. 문제 직전 정상 커밋의 내용을 기준으로 해당 JSON/HTML을 복원합니다.
  4. 복구 후 Pages 배포가 완료되면 Ctrl+F5로 실제 사이트를 확인합니다.

CMS의 각 저장은 GitHub 커밋으로 남으므로 대부분의 콘텐츠 실수는 이전 버전에서 복구할 수 있습니다.

8. 배포·캐시 확인

저장 직후 홈페이지가 즉시 바뀌지 않을 수 있습니다. GitHub Pages 배포가 완료될 때까지 수십 초 정도 기다린 뒤 확인합니다. Chrome에서 이전 버전이 보이면 Ctrl + F5를 사용합니다.

저장 전 최종 체크

① 수정할 항목이 맞는지 → ② 기존 항목을 실수로 삭제하지 않았는지 → ③ 이미지 선택이 실제 필드에 반영됐는지 → ④ Research ID를 불필요하게 바꾸지 않았는지 → ⑤ 저장 후 실제 사이트를 확인했는지 순서로 점검합니다.
